# Release candidate 2.0 — deployment handoff

## Scope and architecture

The user supplied `Anirerepro360-main.zip` and the completed V1.4 mobile source. The candidate preserves the blue/green design, supplied logo, splash rotation/hover, loading states, username login, role-aware dashboard, farm/animal/clinical workflows, reports, offline encryption/idempotent queue, reminders and optional native push. This release adds an animal-level lifecycle workspace with category timeline, actual health measures, grouped hormone results, latest pregnancy and breeding records, and linked mothers/offspring when present in the authorized API responses. It also adds structured fields for previously generic clinical record types, basic input validation, 50-record timeline display increments, runtime server origin configuration and explicit UTC on new companion-server event timestamps. None of these features invent records or determine current pregnancy/diagnoses from historical events. Clinical thresholds, predictive validation and AI/sensor integrations are not part of this release.

## One consolidated candidate

No incremental ZIPs or patch application are needed. Preserve your original project as backup. The `mobile/` tree is self-contained with respect to source; the companion `server/` is already updated. No secrets, user database or default login accounts are included. The old web project remains separate and must use the same deployed API for shared data.

At development/build time the supplied one-click scripts run a controlled automated sequence: create a private verification Python venv, install backend requirements, run source and backend gates on a disposable test DB, generate official Flutter Android/iOS templates if absent, apply native configuration, resolve Dart packages, generate branded icons, run Flutter analyze and Flutter test, then build a debug Android APK or an unsigned iOS device app. All commands are in `tools/release.py`. No earlier overlay steps. The scripts intentionally stop on an error. The CI workflow is included for a standalone repository rooted at `mobile/`; it will not run automatically when nested beneath another GitHub repo. It was authored, not executed. The host still needs Flutter 3.38.4 or a compatible newer SDK, Python 3.11+, Android SDK/JDK and for iOS compatible macOS/Xcode/CocoaPods. The user's macOS Ventura Intel Mac may not support a current Xcode toolchain; iOS compilation/signing may need a newer Mac or macOS CI. The SDK, native Gradle wrapper and resolved `pubspec.lock` are generated on the host, not included in this ZIP. No internet access to download them was available here.

- Android debug output: `build/app/outputs/flutter-apk/app-debug.apk`; after successful build it can be transferred to a compatible Android phone using the usual sideload workflow.
- iOS unsigned device output: `build/ios/iphoneos/Runner.app`; not installable until signed and provisioned. An actual iPhone build or TestFlight distribution requires Apple's signing/registration and compatible Xcode. Store release requires a signed Android AAB and signed iOS IPA, store accounts and current store policy review. Never use debug signing or cleartext HTTP for production.
- Native notification configuration includes Android Internet, notification and boot permissions, icon, desugaring, minimum SDK 23, compile SDK at least 35, and debug-only cleartext overlay. iOS generator configures Keychain entitlements, minimum deployment target 13, debug-only ATS, and notification delegate. Actual plugin/manifest/Gradle/Xcode integrations require native build verification.

## Data and deployment

For a physical debug phone, the login server setting may accept a trusted LAN HTTP origin. The optional `START_TEST_SERVER.command` launches a private, separate test server, with test-only database and generated secrets under `.runtime/`; it is not your online web system. It may bind to LAN only after choosing LAN explicitly. Do not put genuine clinical data or reused passwords into a development HTTP environment. Close any existing process using the same port first; the helper will fail rather than replace a running service. For production, configure HTTPS, PostgreSQL, a persistent session secret and file encryption key, SMTP recovery, backups, CORS, monitored service and role review. The production API URL, deployment credentials and signing keys cannot be inferred or bundled. Use the same existing server/database for both platforms, review the copy against any later backend modifications, and migrate the correct backed-up database. The patch supplied in older releases is only a historical utility and must not be applied again to `server/`.

Backend additions: nullable unique username migration `m20261119_username` already present; server registration/reset minimum 8, usernames normalized, existing email login continues, existing sessions and farm authorization preserved. No passwords have been changed. New writes record UTC; old SQLite timestamps with no timezone are treated as UTC because prior clients generally submitted UTC; any legacy offset-bearing input whose offset was stripped needs administrator review if precision matters. No migration rewrites historical timestamps. Login uses the server's existing eight-hour session and credentials; long passwords/passphrases are preferable. The web UI may retain a 12-character form validation until separately updated.

## Remaining acceptance gates

Source and disposable SQLite backend tests passed; Flutter compiler/analyzer, Dart tests, package resolution, Android/iOS native builds, real device UX, live remote notification service, actual PostgreSQL migration and browser interoperability are not verified in this environment. No APK/IPA has been produced. Firebase/APNs credentials and device provisioning are required for optional remote push; generic local reminders require permission but not Firebase and need real-phone testing. Account recovery delivery requires SMTP. Pending offline records remain encrypted; background synchronization while the app is fully closed, offline attachments, and associating clinical records with unsynced animal IDs remain limitations. Existing reminders are snapshot-based, not critical clinical alarms. No approved research consent dataset, advanced AI or sensor integrations are included. No guarantees of clinical accuracy or production security without review and acceptance. See `QA_FINAL.md` for actual evidence and device checklist.
