# V2.2 — connectivity and publication candidate

## Physical Samsung testing
Keep the existing V2.1 APK/data until you have copied any records you need. This source archive is one `mobile` folder. It includes all earlier changes, not incremental patches. Do not overwrite a live backend/database. Run `START_TEST_SERVER.command` in this folder (Return for localhost), then `TEST_SAMSUNG.command` with the USB phone connected. The helper validates local API, detects authorized physical devices, repairs platform templates, checks Flutter, restores ADB reverse, and launches with `API_BASE_URL=http://127.0.0.1:8000`. An eight-second, unauthenticated app health probe tests the real API before authentication. The login page shows the selected origin and offers Test connection; debug builds can change server even when a build-time origin is supplied. USB forwarding is not persistent across disconnection, and the helper cannot prevent a cable failure during the build. In that case rerun ADB reverse and install the existing debug APK; see SETUP.md. No emulator default is silently used. New builds use a new server-preference key; an account session remains isolated by origin. Debug HTTP is for fictional data and credentials only. No public cleartext fallback or TLS bypass is included.

## Hosting (required before public release)
The backend must run independently of a development computer. The bundled `server/Dockerfile` is a portable candidate for managed Docker hosting; it has not been container-built here. Use a managed PostgreSQL database, persistent attachment volume writable by the container user, and a public HTTPS endpoint with trusted certificate. Use a reverse proxy/managed ingress, avoid logging OAuth callback URLs or secrets, configure proxy rate limits and monitoring. Back up and reconcile migrations with the CURRENT shared web backend before applying them; the snapshot in this ZIP is not a verified match for later web changes. Never run competing independent databases expecting automatic shared records.

1. Set server environment via hosting dashboard: `APP_ENV=production`, `DATABASE_URL=postgresql+psycopg://...`, `SESSION_SECRET` (random persistent secret >=32 characters), `FILE_ENCRYPTION_KEY` (random base64 32 bytes), `ATTACHMENTS_DIR` (persistent storage), SMTP_HOST/PORT/USER/PASSWORD/FROM, `RESET_URL_BASE` and `INVITE_URL_BASE` (working HTTPS web destinations), `CORS_ORIGINS` (actual HTTPS web origin), `ALLOW_INITIAL_SETUP=false`. Do not put real secrets in source control. Plain postgres:// and postgresql:// hosting URLs are normalized to the installed psycopg driver. See .env.example and SOCIAL_AUTH.md. If the host provides a dynamic port, set its start command to `python -m uvicorn app.main:app --host 0.0.0.0 --port "$PORT" --no-access-log`; otherwise route to 8000.
2. On a new isolated staging database first, run `python -m alembic upgrade head` once in the server container. Back up and assess the existing database before any production migration. Run the server. Visit `https://YOUR-REAL-API-HOST/api/health`; require `{"status":"ok","service":"anirepro-api"}`. This check is liveness, not proof of database/SMTP readiness. Verify staging registration, login, farm data, permission isolation, email delivery, backups/restore and real device synchronization over mobile data.
3. Configure Google and Apple OAuth, Firebase/APNs and a push worker if those features will ship. Absent provider credentials, buttons cannot complete OAuth; do not advertise enabled features. Paid Apple Developer enrollment is needed for Apple provider configuration/distribution. Never bypass HTTPS. For now use password credentials.

## Android store candidate
The native generator now checks critical platform files rather than directory existence; incomplete folders are backed up outside the mobile project. It reapplies native networking/notification configuration and sets Android target/compile SDK to at least 36. Install matching Android SDK/platform tools. Preserve the same package/application ID if already published. Google Play requires a signed AAB, not the debug APK. Keep the upload keystore in a protected location and never commit credentials. Generate an upload key via Android Studio's signing wizard or use an existing upload key. Create YOUR local `android/key.properties` (ignored by Git): `storeFile=/absolute/path/to/upload.jks`, `storePassword=...`, `keyAlias=...`, `keyPassword=...`, one per line. Generate native projects first using setup if needed. Run `python3 tools/build_store.py --api https://YOUR-REAL-API-HOST`. The script aborts if the API health check or signing config is missing; it builds release AAB with the fixed public origin. Output `build/app/outputs/bundle/release/app-release.aab`. Build script, signing, native compiler, and AAB are unverified in this environment. A healthy endpoint is not proof of deployment security. Inspect bundle signing and target SDK in Console.

## Publication blockers — not a 100% ready app
- Confirm Android native release compilation, signing and actual Samsung install; test with USB removed over mobile data. Run new and existing Flutter tests on device/SDK. Test loss/recovery of network, account sessions, queued writes, no duplicate records, all clinical workflows, access control, report export, local reminder permissions, real SMTP/OAuth/push provisioning.
- Production HTTPS/PostgreSQL deployment, web integration, data retention and backup verification remain unperformed. Required credentials and actual domain are not supplied.
- Account deletion (inside app and accessible external deletion request), data retention/privacy policy and support contact, terms and Data safety disclosures require completion before Google Play publication; do not submit fabricated declarations. Account deletion must account for farm-owned/shared clinical data and retention policy. This release does not implement deletion or linked-provider revocation. Review social login branding and availability, Apple review and iOS signing separately.
- For eligible new personal Play accounts, closed testing requires at least 12 opted-in testers for 14 continuous days, per https://support.google.com/googleplay/android-developer/answer/14151465. Check current target SDK and policy in Console: https://support.google.com/googleplay/android-developer/answer/11926878. Android 16 target API 36 configured, not compiler-verified.
- Existing limitations from V2.1 remain: no full closed-app background synchronization, offline attachments, or live provider verification. This package is a release candidate, not a signed APK/AAB/IPA, nor a guarantee of approval.
