# Revision 1.3 — Offline capture and foreground synchronization

This cumulative update includes revisions 1.0–1.2. Overlay it onto the existing `mobile/` folder; preserve generated `android/`, `ios/`, `.metadata`, signing files, and `pubspec.lock` (the next dependency resolution updates the lockfile). No backend or web file is replaced. No new server migration is required for offline sync. The existing optional username compatibility migration is separate.

## Using the offline workspace

1. Connect to the real API and sign in. Enable Keep me signed in if you need to reopen the workspace without a connection. Use a personal device with a strong OS screen lock.
2. Select the farm. Open Dashboard → cloud sync icon or More → Sync center → Prepare this farm for offline use. The app requests the farm summary, animal registry, accessible clinical feeds, profile and species reference. Open individual animal histories/cycle pages online if you need those snapshots later. Large datasets may exceed cache limits; verify critical views before leaving connectivity. The farm-wide events endpoint is subject to the existing server's 500-record limit.
3. If the API is unreachable, an offline banner appears. Only cached views are available; they are snapshots, not live server truth. Reports and metrics reflect saved server data, not pending records. Offline-only submissions appear separately in Sync center.
4. Register animals or submit clinical events for existing server-identified animals using the normal forms. Each supported submission is encrypted and persisted locally **before** a network request. A queued submission message means it is not server-confirmed.
5. When online again, open Sync center → Sync now or leave the app open. It attempts synchronization at app resume and approximately every 45 seconds in the foreground while offline or when retryable records are pending. No OS background worker is installed. It verifies the session and fresh farm membership before replaying queued requests. Refresh your screens after sync; the banner continues to flag possible saved views after reconnecting.
6. Conflicts, permission failures and validation errors remain in Needs review; no silent overwrite or automatic payload rewriting. Open the record, read the server response, and retry with its original key or explicitly discard the local entry. A corrected submission requires a new record; check the server first, particularly after a timeout. Discard does not delete anything on the server.

## Supported scope

- Cached farms, dashboard, animal registry, individual animal event histories, clinical feeds (health, reproduction, breeding, pregnancy, births, tasks), cycle summary, species reference and profile. A cached report can display the underlying saved views; server exports require a connection.
- Queued POST to `/api/farms/{farm_id}/animals` and `/api/farms/{farm_id}/animals/{animal_id}/events`. The API supports `X-Idempotency-Key` for both; replay uses the exact original path, payload and stable key. The backend owns record IDs and permission checks. Clinical confirmation remains subject to server role/evidence requirements. Delivery/offspring creation is transactional when supported by the existing API.
- No local temporary animal IDs or dependent clinical submissions for a not-yet-synchronized animal. Sync the registration first. File uploads/downloads, archive/delete, account changes, invitation/team management, notification actions, recovery, registration/login and exports require internet. In-app notifications are not cached. No push notifications or closed-app sync.

## Storage and session policy

- AES-256-GCM authenticated encryption using `cryptography` (new dependency). Random key held in platform secure storage; iOS uses device-only unlocked accessibility. Cache and queue are separated by API origin string and user ID, not a global shared file. Atomic same-directory replacement and serialized writes preserve previous state if encryption/persistence fails before replacement. This is a small encrypted file store, not SQLite; bounded for the current workload (80 cache entries, 8 MiB snapshot budget, 12 MiB total serialized data, 300 pending writes). Oversize snapshots may be evicted, never pending records. Device-level filesystem durability under sudden power loss and OS backup behavior require platform acceptance tests.
- Snapshots expire after 24 hours; actual offline workspace access is also limited to the server token expiry (existing token lifetime is **eight hours** from login), and the last server-verified identity. The client never extends server token life offline. No offline password verification or first-time offline login. Restart access requires remembered session + cached farms. Offline access is a bounded convenience, not a substitute for fresh permission checks; revocations cannot be known until connectivity returns. No biometric/PIN app lock, remote wipe or multi-device local-data export is shipped.
- On 401 the app clears its active session; fresh login to the same account recovers its queue. Known 403 responses invalidate cached views. Membership changes invalidate old snapshots and rebuild the workspace. Logout clears cached views and removes stored session/identity, but retains encrypted pending submissions for the same account; the UI warns before logout when pending items exist. Offline logout cannot invalidate the server token immediately; it removes local access. Uninstalling, clearing app data, losing keychain keys or changing server URL can make queued data inaccessible. Sync all pending records before reinstalling/changing environment. If an encrypted file is corrupted or key missing the app refuses to open it rather than silently reset the queue.

## Testing status and acceptance

The Python server contract smoke test was actually run on a disposable SQLite copy of the supplied backend and passed (animal and event replay, changed-payload conflicts, transactional delivery/offspring replay, unauthenticated replay rejection). It is included as `tools/test_sync_contract.py`; run only with a development backend dependency environment. Eight Flutter unit tests are provided for encryption, restart persistence, key reuse, conflicts, concurrent local writes, cache boundaries and tampering. They have **not** been run here. Flutter SDK/device not available; all V1.3 Flutter dependency resolution, analysis, builds and native keychain behavior remain unverified. Do not use for live clinical capture before real device acceptance.

When physical devices are available, test both Android and iOS, including online preparation, airplane mode on an already signed-in workspace, cached views, process termination/restart, expired session, different account/farm and revocation, offline entry creation, a failed local storage write, reconnect, duplicate replay after lost response, server errors/409/422, sign out and recover pending records using the same account, and exact mobile/web count reconciliation. Confirm the app never shows a queued record as server-confirmed and never exposes another account's records. Repeat tests with actual HTTPS API; a development URL such as `10.0.2.2` is emulator-only.
